## 1. GlucoTwin: evidence before action

This explanation uses a disclosed synthetic voice. The interface images are actual captures of the current local research application. GlucoTwin is a patient-specific glucose research platform designed around a simple evidence chain: observe a patient, forecast an upcoming glucose excursion, let a reviewer inspect the evidence, and compare that forecast with the eventual measurement. Our recommendation remains GlucoTwin because its public patient-linked data supports a concrete, understandable chronic-condition demonstration. The product now extends beyond a replay chart into a clinician workspace, patient companion, administration controls, durable intake and immutable forecast receipts. These are implemented local capabilities, not evidence of clinical readiness. We currently have no physical continuous glucose monitor and no authorized clinic data connection. The live source is therefore a partnership dependency, and the application explicitly keeps clinic connections pending. Public recordings and labelled synthetic arrivals let us evaluate the engineering without pretending they are current patient care. The distinguishing idea is visible, auditable adaptation with honest uncertainty and abstention. We show what was known when a forecast was made, which model produced it, how much lead remained, what the reviewer recorded and whether the later observation supports the prediction. Winning the challenge requires that complete story, alongside reproducibility and truthful evidence boundaries.

## 2. Fit to the published challenge

The published challenge asks for a focused chronic-condition digital twin combining historical patient information with a dynamic sensor stream, predicting a localized adverse outcome and exposing a usable doctor-facing interaction. GlucoTwin addresses those requirements through Type 2 diabetes, matched demographic context, native continuous glucose monitoring observations and a defined upcoming high-glucose-excursion label. The thirty-minute horizon is our primary target, and sixty minutes is supplementary. These are declared project choices, not numerical judging weights or a guaranteed winning formula. The brief accepts public or synthetic data, so those modes support an honest hackathon demonstration while a future authorized source is pursued separately. We make the twin's updates visible, compare it with stronger baselines, expose uncertainty, and preserve a reviewable record instead of relying on a polished prediction number alone. The submission also includes architecture, a public repository with reproducibility instructions, an open-source license, presentation files and a sufficiently long explanation and demonstration recording. The organizer's page remains the authority for entry details. We should check it again before submission because deadlines and instructions can change. Our materials map existing features to the published requirements without claiming an official weighted score.

## 3. The clinic journey we are preparing

The primary product journey starts with a care-team reviewer opening the queue. A review item distinguishes an observed high reading, a predicted future excursion, a data-quality concern and an ordinary forecast receipt. The reviewer opens the patient record to inspect recent observations, available historical context, the forecast horizon and the source's freshness. The model's output is evidence for review rather than a treatment instruction. The reviewer can acknowledge an item, document a reason and note, plan a follow-up and later close the episode. Each change has an audit record. A consultation summary closes the workflow with a portable PDF. This is the workflow we want a partner doctor to review before any clinical activation. That review has not occurred yet, and the configured staffed hours do not establish that an actual clinic is providing a monitored service. The hackathon core demonstration uses a selected recorded episode so judges can see the prediction and eventual outcome quickly. Separate synthetic wall-clock intake demonstrates the operational system. Keeping those clocks visible matters: a replay from an old public recording is not a current clinical warning, and a synthetic source is not a patient's sensor.

## 5. Historical context without future leakage

Historical context has to obey a time boundary just as sensor data does. A result measured before a forecast but received afterward was not available to the forecaster at issue time. The source study allows laboratory collection within a window that can extend after monitoring, so untimed laboratory values are excluded from prediction features. The population model uses allowlisted age, sex, body mass index and diabetes duration, with the public dataset's availability assumptions disclosed. New structured historical context is dated and has provenance. The arrival worker uses its trusted receipt time to prevent a backfilled entry from changing an earlier issuance. Patient meal, activity and symptom entries remain explicitly self-reported timeline context; they do not silently become inputs to a validated meal-response or treatment model. Clinician-approved shared notes are similarly distinct from private assessment notes. The current implementation can demonstrate historical-context and dynamic-glucose fusion, but that integration does not prove predictive benefit. The evaluations preserve context ablations and unfavorable findings. For an authorized clinic source, untimed baseline information would be excluded until its availability can be established. This is a practical design constraint and a central methodological safeguard.

## 6. An architecture with an evidence ledger

The architecture separates collection, forecasting, storage and interaction while keeping the code understandable for a hackathon team. A source event arrives through a scoped connection. Intake validates identity, timestamps, units and duplicate behavior, then commits the accepted measurement and forecast job together. The worker reads only the prefix available at its issue clock, obtains the model output and stores an immutable receipt. Observed outcomes are appended later instead of rewriting the original prediction. The clinician workspace, patient companion and administration views read different projections of that same stored evidence. FastAPI provides the backend, Python libraries implement the research model, and React with TypeScript, Tailwind and Recharts provides the interface. SQLite is the default local store, with a separately tested PostgreSQL path. Operational metadata events allow the interface to refresh without exposing raw health payloads through the event channel. Source quality, model identity and forecast timing travel with each receipt. That makes the architecture diagram meaningful: it represents actual boundaries and persisted records, not a collection of future cloud services. Hardware integration, encrypted clinical hosting and approved prospective evaluation remain outside the demonstrated release.

Source notes: docs/ARCHITECTURE.md; backend/OPERATIONAL.md

## 7. Three clocks that must stay visible

A live-oriented forecast has several timestamps that cannot be collapsed into one. Measurement time says when the source sampled glucose. Trusted server receipt says when the application first knew the reading. Issue time defines the available input prefix used by the forecast. Target time says which future native reading the model predicts. For the existing model, the target is anchored to the latest measurement, not automatically to the current server time. A reading measured at ten o'clock and issued at ten oh one still targets ten thirty for the thirty-minute model, leaving twenty-nine minutes. The application exposes that remaining lead instead of presenting an exact thirty-minute-from-now promise. Recorded research playback has a labelled virtual clock; wall-clock synthetic arrival receipts have a different explicit clock kind. All arrival timestamps require an offset or Z and normalize to UTC. Source-local time affects time-of-day features, but compatibility with the public cohort's unverified local training clock remains unvalidated. That is why timezone and end-to-end latency are required source-verification gates. These timestamps make late delivery, backfill and forecast comparisons understandable and prevent a superficially live interface from concealing stale evidence.

Source notes: docs/LIVE_MODEL.md

## 8. Cadence and abstention are product features

The saved model expects five actual consecutive native fifteen-minute readings. That contract is deliberately explicit. A five-minute or one-minute source is not accepted by interpolating, averaging or automatically inventing a compatible history. A faster synthetic generator can demonstrate intake arrivals, but its prediction status is unsupported cadence. A missing native slot creates a gap, and readings older than twenty minutes pause the arrival adapter. Those thresholds are engineering policy for this research release, not clinical standards. Endpoint estimates require at least ten minutes of remaining lead. Event probabilities are stricter because their original target list includes intermediate native readings. If any of those targets is at or before the actual issue time, the entire corresponding event probability is suppressed. A probability concerning an original window partly in the past cannot be relabelled as a new future event. For synthetic research review, the earliest target must still have at least ten minutes of lead and the primary thirty-minute signal must meet the declared threshold. Missing-data and unsupported states are visible outcomes. An abstention should never appear as a reassuring low-risk value. This improves both the demonstration's honesty and the future source-validation plan.

Source notes: docs/LIVE_MODEL.md; backend/OPERATIONAL.md

## 9. A twin that shows how it changes

The original prototype includes a local-trend state model with Kalman measurement updates. It tracks glucose level and recent change and shows how an incoming observation corrects the estimated state. That is an engineering approximation of the glucose trajectory; it does not model organs, insulin physiology, medication effects or causal treatment responses. The stronger forecasting path combines a population gradient-boosted predictor with a bounded patient-specific residual correction. The correction uses discrepancies between predictions and their later matching native observations, shrinks toward zero and is limited to avoid unbounded drift. Arrival mode tightens that rule further: only actual stored issuances and outcomes already received by the current clock may update adaptation. Historical observations alone do not create imaginary earlier forecasts. Separate accumulators serve the thirty- and sixty-minute horizons, and repeated deliveries or repeated target forecasts are not counted multiple times. The interface can expose level, trend, volatility, adaptation maturity and correction history. The contribution is an observable and auditable evolving patient model. Whether that adaptation improves prediction is answered by experiments, with an experimental label when the evidence does not support promotion to the primary model.

## 11. Predict a defined event, then calibrate it

Our adverse-event label is deliberately narrow: any scheduled native future glucose reading above one hundred and eighty milligrams per deciliter within the declared horizon. This is a research label, not a diagnosis or an emergency definition. A dedicated classifier estimates the probability of that event, while the regression model estimates the future endpoint value. These are different tasks: an excursion can happen at the intermediate reading and resolve before the endpoint, so a single endpoint threshold can miss it. We also distinguish an ongoing observed high reading from an advance warning for a currently below-threshold patient. Event calibration asks whether the displayed probabilities correspond to empirical frequencies. Prediction intervals address uncertainty around future glucose values. The nominal interval target and the warning threshold are selected using calibration information under the frozen evaluation protocol, not optimized after observing each test patient. The declared false-alert budget is provisional engineering policy. Aggregate calibration does not guarantee an individual forecast, and arrival mode explicitly marks transferred probability calibration and interval widths unvalidated. The benchmark view exposes these qualifications so a clear-looking probability or shaded band does not imply more assurance than the data support.

## 13. Arrival stress changed our model choice

We tested the arrival adapter with twenty sampled public patients, three sparse synthetic issuances per patient and four assigned delivery delays: zero, one, five and twenty minutes. The experiment assigns a clock for testing; it does not measure real sensor latency or establish the source timezone. Each scenario passed sixty reordered-prefix checks and sixty unavailable-backfill invariance checks. Forty exact thirty-minute targets were scoreable in each scenario. On that small functional sample, population mean absolute error was about twelve point five five zero, while the actual-issuance hybrid was twelve point six seven six. Adaptation was slightly worse. That negative result matters: the modest retrospective hybrid gain is not transferred into a live-oriented marketing claim. Population forecasting stays primary for arrival mode, with the hybrid visibly experimental. At twenty minutes of delay, an endpoint still had ten minutes remaining, but the first original event target was already past, so both event probabilities were suppressed. No scenario created a clinically eligible queue item. The experiment establishes temporal behavior and exposes a model limitation. A new genuine issue-time forecasting model would need verified device timing, a new frozen future-only label protocol and fresh evaluation before replacing this cautious adapter.

## 14. The clinician view closes the loop

The clinician interface brings three kinds of evidence together without merging their meanings. Observed glucose is a measurement. A forecast is a stored model estimate issued using an available prefix. A review state is a person's documented response. Reviewing or closing an item does not change the prediction or manufacture a correct outcome. The patient view shows recent history, model comparisons, quality status and relevant context, while the queue retains review ownership, follow-up timing and episode history. Repeated concerns update an existing episode and link the latest receipt rather than endlessly duplicating the same work. A revision number prevents two reviewers from silently overwriting one another's actions. Later point outcomes and complete-window event outcomes are appended separately, which allows an intermediate late reading to complete an event label without rewriting an earlier receipt. The consultation PDF uses the same underlying evidence as the screen. During the recorded core demonstration we can show an advance warning, move to the eventual measured outcome and then export the record. The full explanation also includes a stable episode and a sensor gap so the interface is assessed for abstention and failure behavior, not only a favorable example.

## 16. A patient companion with a limited view

The patient companion is an implemented part of the platform, but its permissions are intentionally different from the clinician workspace. A patient account is bound server-side to its own clinic record. It can inspect its own recorded readings, add a meal, activity or symptom note, see clinician-approved shared notes, complete its own published tasks and export a patient-visible summary. It cannot read the clinic queue, another patient's evidence, staff administration or private assessment notes. Model forecasts are excluded from the companion, and predictions remain disabled. That avoids presenting an experimental research estimate as direct patient advice. The current companion identity is fictional and clearly labelled synthetic. Self-reported entries carry provenance and a receipt time instead of becoming verified sensor facts. A consent history records research collection choices; withdrawal revokes the relevant bound source credential. A consent record does not activate clinical monitoring or replace outstanding approvals. Published follow-up instructions require an authorized care-team role, while draft tasks stay hidden from the patient. These capabilities let us demonstrate a complete platform relationship without claiming that it is operating with real patients. Doctor review, source access and a suitable clinical protocol remain required before that boundary can change.

Source notes: docs/API_CONTRACT.md; backend/tests/test_platform.py

## 17. Administration and access have real controls

Administration includes synthetic enrollment, individual account invitations, source configuration, intake preview, access revocation and audit review. Invitations use a private manual handover rather than pretending an email service has been integrated. Care-team, coordinator and patient roles have different access. Cookie authentication uses HttpOnly SameSite Strict cookies and mutation CSRF checks. Optional time-based verification codes protect subsequent sign-ins once enrolled, with secrets encrypted in the local store. Enabling verification revokes other existing sessions, and deactivating an account revokes its sessions. Failed sign-ins are throttled by the implemented local policy. Synthetic connections receive a scoped ingestion key once; that key cannot read clinic records or act on another source. A revoked connection cannot be resumed through the ordinary status action. The application also keeps clinic device connections pending without an intake credential. These are tested local safeguards, not a declaration of production security. The legacy bearer route remains a compatibility path with a separate session-policy boundary. HTTPS hosting, broader abuse protection, managed secret rotation, recovery policy, operational roles and retention procedures still need deployment review. Demonstrating actual controls is stronger than claiming that authentication alone makes a medical platform ready for release.

## 18. Recoverable data and traceable model releases

Local persistence is recoverable rather than an in-memory demonstration shortcut. SQLite remains the default, using foreign keys, WAL and versioned schema upgrades. The actual PostgreSQL path uses SQLAlchemy and Alembic, with both fresh installation and a version-six-to-seven upgrade tested in an isolated PostgreSQL sixteen point fourteen database. Append-only guards protect issued evidence. The PostgreSQL readiness probe confirms connection and schema, not a database integrity audit, and its backup and failover procedures are not yet verified. For SQLite, the encrypted backup script takes a consistent snapshot, includes a checksum manifest and encrypts the archive. Offline restore requires a new destination, the original key and successful integrity verification; it does not overwrite the old runtime database. Backup encryption does not encrypt the application database itself, and off-host recovery remains unverified. Model selection verifies an approved artifact hash, archives the previous model and replaces the selected file atomically. Both API and worker must restart because model objects are cached. A checksum identifies trusted bytes; it does not establish predictive quality or clinical authorization. These operations give the team concrete recovery and rollback steps while leaving deployment readiness honestly pending.
